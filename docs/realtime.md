# Работа со звонками в реальном времени — исследование (черновик)

> Статус: **черновик**: заполнены подходы A–D (шаги Б1, Б3), раздел «Расширение браузера» и «Ограничения платформ». Потоковая транскрибация (Б2) измерена и внесена (раздел 3); живая саммаризация (Б4) — раздел 4 (заглушка + один короткий прогон на Codex CLI).
> Это исследование, а не функция: продуктовый код в `src/` не менялся, прототипы лежат в
> [`prototypes/realtime/`](../prototypes/realtime/README.md).
> Все проверки по документации сделаны 2026-10-23; что проверить не удалось — помечено «не проверено».

## 1. Цель

Понять, как получать звук звонка (Яндекс.Телемост, Google Meet, Discord, Microsoft Teams) на Windows, опционально
транскрибировать его потоком и периодически коротко пересказывать (саммаризация «на лету»), не пытаясь превратить
Diarrhizer в клиент этих платформ. Итог — сравнение подходов, измерения и рекомендация MVP (раздел 7).

## 2. Подходы A–D

| | Подход | Статус |
|---|---|---|
| A | Системный loopback Windows (WASAPI) + микрофон, без интеграций с платформами | **исследован (Б1), см. 2.1** |
| B | Браузерное расширение: звук вкладки (`tabCapture`) + микрофон → локальный приёмник | **прототип (Б3), см. 2.2 и раздел 5** |
| C | Бот-участник через API платформы | анализ по документации (Б3), см. 2.3 и раздел 6 |
| D | Гибрид: звук локально (A/B) + имена и метаданные у платформы / из страницы | анализ (Б3), см. 2.4 |

### 2.1. Подход A — системный loopback + микрофон

**Идея.** Любой клиент звонка воспроизводит голоса собеседников через звуковое устройство Windows. WASAPI loopback
отдаёт то, что устройство вывода проигрывает (смесь всех приложений), а микрофон пишется отдельно. Получаются две дорожки:
**«я»** (микрофон) и **«остальные»** (loopback) — без API платформ, без ботов, без учётных записей.

#### Сравнение способов получить loopback из Python

| | PyAudioWPatch 0.2.12.9 | soundcard 0.4.6 | sounddevice 0.5.6 |
|---|---|---|---|
| Loopback | **да** (`get_default_wasapi_loopback()`) | **да** (`get_microphone(id, include_loopback=True)`) | **нет** — в `WasapiSettings` нет параметра `loopback` (колесо PortAudio без патча) |
| Модель | callback-потоки, ничего не блокирует | блокирующий `record()`, нужен поток на источник | — (годится только для микрофона и воспроизведения) |
| Формат | выдаёт нативный mix-формат (здесь 48 кГц, 2 кан., float32 по запросу) | сам ресемплирует в запрошенный | — |
| **Тишина** (ничего не играет) | **пакетов нет совсем**: 10 с тишины → 0 колбэков; 23 блока за 10 с «нет звука» при хвосте предыдущего воспроизведения; шкалу времени надо дополнять нулями по часам | сам выдаёт нулевые блоки: 10 с тишины → 200 блоков | — |
| Тишина, но в системе идёт поток нулей (обход) | пакеты идут (196 блоков за 10 с) | не требуется | — |
| Первый пакет после старта | 0,33 с | 0,32 с (при звуке), 0,10 с (тишина) | — |
| Пропуски/«разрывы» (4 мин, тихая машина, шум играет) | флаг overflow: **0**, потерь 0 | предупреждений «data discontinuity»: **6** за 4 мин (**46** за 30 мин) | — |
| CPU (30 мин / 4 мин), % одного ядра | **0,37 / 0,56** | **1,54 / 2,27** | — |
| RSS | 46 МБ | 44 МБ | — |
| Зависимости | колесо с PortAudio внутри (cp312, win_amd64) | чистый Python на cffi + numpy | колесо с PortAudio, но без loopback |
| Смена устройства | поток привязан к индексу; список устройств PortAudio фиксируется при инициализации — после смены нужно закрыть **все** экземпляры `PyAudio` и создать заново | поток привязан к устройству; новый `default_speaker()` читается свежо | — |

Выбор для прототипа: **PyAudioWPatch** — callback-режим, ноль потерь и в 4–6 раз меньше CPU. Его слабое место (нет пакетов
в тишине) закрыто в `capture.py` общей шкалой времени: каждый блок кладётся на позицию «время прихода − T0», пропуск
превращается в нули. Альтернатива без этой логики — soundcard (проще код, но больше нагрузка и «разрывы»).

#### Что пишет `capture.py`

Две моно-WAV 48 кГц PCM16 (`mic.wav` — «я», `loopback.wav` — «остальные»), одинаковой длины на общей шкале времени,
плюс `stats.csv` и `summary.json`. Ограничение: при уходе одной дорожки больше чем на 150 мс блок обрезается/дополняется
нулями (жёсткий шов ≤ 100 мс). Это достаточно для ASR/диаризации, но не для эхоподавления.

#### Дрейф между дорожками, 30 минут (1785 с анализа, 358 точек)

| | PyAudioWPatch | soundcard |
|---|---|---|
| Микрофон vs часы ПК | **+109 ppm** | +111 ppm |
| Loopback vs часы ПК | −1,4 ppm | −0,4 ppm |
| loopback − микрофон | **−110 ppm** | −111 ppm |
| Расхождение за 30 мин (по точкам 5 с) | 250 мс (шаг дискретизации ±50 мс) | 200 мс |
| Ожидаемое по регрессии (110 ppm × 1785 с) | 197 мс | 197 мс |
| Длины итоговых файлов | mic длиннее loopback на 92 мс (4422 кадра) | mic длиннее на 116 мс (5553 кадра) |

То есть USB-микрофон «уходит» на ~6,6 мс в минуту относительно loopback (оба бэкенда видят одно и то же — это свойство
устройств, а не библиотек). Для ASR и диаризации это несущественно (≈0,2 с за полчаса), для сведения дорожек в одну
по времени реплик — тоже; для эхоподавления потребовалась бы передискретизация по измеренному ppm.
**Один микрофон и одна гарнитура — это один набор устройств; на других устройствах ppm будет другим.**

#### Нагрузка, формат, потери

* Формат устройств: loopback — mix-формат устройства вывода (**48 000 Гц, 2 канала**), микрофон — 48 000 Гц, 2 канала;
  у виртуального «DroidCam» микрофона — 16 000 Гц, 1 канал. Прототип сводит в моно и хранит 48 кГц/PCM16
  (**5,76 МБ/мин на дорожку**, 173 МБ за 30 мин). Для WhisperX потребуется ресемплинг в 16 кГц (в проде это делает FFmpeg-стадия).
* CPU: PyAudioWPatch **0,37 %** одного ядра за 30 мин (0,02 % всей машины), soundcard **1,54 %**. Память ~45 МБ, не растёт.
* Потери: PyAudioWPatch — 0 overflow за 30 мин и 4 мин; soundcard — 46 предупреждений «data discontinuity» за 30 мин
  (что именно потеряно, не выяснено: счётчик кадров совпал с ожидаемым).
* Тишина: ни одна библиотека не «зависает»; но у PyAudioWPatch поток пакетов в тишине прерывается (учтено шкалой времени).

#### Смена устройства вывода

Проверено вручную (оператор переключал вывод по умолчанию в Windows во время записи), `capture.py --follow-devices`
(опрос устройств по умолчанию раз в секунду, повторное открытие обоих потоков), тихий шум играл на текущее устройство вывода,
запись 150 с, PyAudioWPatch:

| Момент | Событие | Результат |
|---|---|---|
| 7,9 с | вывод: Strix Wireless Headset → Динамики Realtek | смена обнаружена, потоки переоткрыты за **0,25 с** (7,89 → 8,14 с), в loopback-дорожке тишина **0,3 с** (7,8–8,1 с) |
| 52,4 с | обратно на Strix Wireless Headset | переоткрытие за **0,17 с** (52,38 → 52,55 с), пауза в loopback короче 0,2 с (порог анализа 0,1 с-окон) |

Итого 2 переключения → 2 перезапуска, потеряно по ~0,2–0,3 с на каждое, без падений и без ручного вмешательства; обе дорожки
остались одной длины (150,01 с) на общей шкале времени. Микрофон при этом тоже теряет те же 0,2–0,3 с (прототип
переоткрывает оба потока, потому что PortAudio обновляет список устройств только после закрытия всех экземпляров).
Задержка обнаружения — до 1 с (период опроса); аудио на новое устройство в этот интервал не терялось заметно, потому что
источник звука начал играть на новое устройство сразу. Без `--follow-devices` поток остался бы привязан к старой
конечной точке (не измерялось; следует из того, что loopback открывается на конкретной точке: [Microsoft: Loopback Recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording),
стр. от 2025-04-16).

**Не проверено:** физическое извлечение/подключение наушников (устройство исчезает, а не переключается по умолчанию),
отключение звука (mute) мастер-громкости **вывода**, смена **микрофона** по умолчанию (mute **микрофона** проверен — см. «Результат: Google Meet»). Если клиент звонка выводит звук не на устройство
по умолчанию, loopback по умолчанию будет пустым (в Teams, Meet и Телемосте вывод выбирается в настройках, см. таблицу ниже).

#### Process loopback (звук одного процесса)

Windows умеет захватывать звук **одного процесса и его дочерних** (или всего, кроме него) через `ActivateAudioInterfaceAsync`
с `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS` (режимы include/exclude process tree). Не привязан к конечной точке вывода, чужие звуки
(уведомления, музыка) исключаются; процесс без звука даёт тишину
([пример Microsoft](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/),
обновлён 2026-02-20).

* **Минимальная версия по документации — Windows 10 build 20348**
  ([AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_process_loopback_params),
  стр. обновлена 2024-02-22; тот же порог в примере). Версия «с Windows 10 2004 (build 19041)» из постановки **официальной
  документацией не подтверждается**.
* Готовый путь из Python есть: пакет [`proc-tap`](https://pypi.org/project/proc-tap/) 1.1.1 (релиз 2026-07-22, MIT, колёса
  cp312 win_amd64, нативное расширение на C++): `ProcessAudioCapture(pid, on_data=...)`, формат 48 кГц stereo float32.
  README на PyPI устарел (упоминает `StreamConfig`, которого в 1.1.1 нет). Своя нативная обёртка не обязательна.
* **На этой машине (build 19045) фильтрация по процессу не работает.** Эксперимент: Chrome (отдельный профиль) играет речь,
  другой процесс в это время играет тон 1 кГц.
  `proc-tap` по PID Chrome: доля энергии на 1 кГц во время тона **0,910**, RMS до/во время/после тона 0,0116/0,0693/0,1114;
  системный loopback: **0,905**, 0,0117/0,0689/0,1116 — то есть чужой тон не исключён, захват идентичен системному.
  Отрицательный контроль: PID молчащего процесса (сам скрипт) даёт RMS 0,00938 при пике 0,116 (речь Chrome) — не тишину.
  В исходниках `proc-tap` объяснение: при build ниже 20438 он **молча переключается на захват всей системы** (предупреждение
  только в `OutputDebugString`). Код возврата успешный — легко не заметить.
* Минусы: нужен PID (у браузера звук играет в дочернем процессе — нужен режим include process tree); приложение должно
  быть запущено и играть; нельзя выбрать «вкладку Meet» из общего процесса браузера; нативная зависимость от стороннего
  пакета; на Windows 10 22H2 бесполезно. Плюс: исключает уведомления и чужую музыку на Win11/сборках ≥ 20348 (**там не проверялось**).

#### Что даёт разделение «я»/«остальные» для диаризации

Это оценка по устройству решения, не измерение на разговорах (в рамках шага нет многоголосого материала).

* Даёт: диаризация «я» не нужна — дорожка микрофона и есть говорящий; в дорожке loopback остаётся диаризовать только
  собеседников (меньше путаницы, чем в смеси); перекрытие речи (я говорю одновременно с кем-то) не теряется, а видно как
  активность обеих дорожек; можно считать долю времени каждой стороны без модели.
* Не даёт: loopback — **одна** дорожка для всех собеседников, их различение остаётся задачей pyannote; клиент может нормализовать/сжимать
  голоса (авторегулировка усиления, подавление шума) — это видно в loopback, не в исходном голосе; нет привязки голоса к имени
  участника (в отличие от API платформ).
* Риск: при **открытых колонках** голос собеседников попадёт и в микрофон («эхо» в дорожке «я»), клиенты пытаются подавить его эхоподавителем,
  но остаток разрушает чистоту разделения. С гарнитурой это не проявилось: речь через наушники при записи дала средний уровень
  микрофона 0,00305 против 0,00344 в тихом прогоне без речи (шум комнаты), когерентной копии loopback в микрофоне нет (0 из 10 окон,
  `analyze_tracks.py`). Детектор проверен на синтетике: «наушники» 0 из 20, «колонки с утечкой −10 dB» 14 из 20.
  [Microsoft](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording) указывает, что loopback в WASAPI
  введён в первую очередь для эхоподавления — loopback можно использовать как опорный сигнал AEC (не реализовано).

|---|---|
| Речь собеседника в loopback | **да**: активна в 29–60 с, RMS 0,083 (средняя за окно), пик за запись 0,985 |
| Свой голос в loopback (эхо от клиента) | **нет**: пока я говорил один (0–28 с), RMS loopback 0,0005 против 0,083 при речи собеседника; корреляция моего голоса с loopback в окне ±2,5 с: максимум 0,30 (порог 0,35 не превышен, контроль на несвязанной речи — 0,24, т. е. на уровне метрики) |
| Речь собеседника в дорожке «я» (утечка из наушников) | **нет**: 31–56 с микрофон — цифровой ноль (см. ниже); в окнах «говорят оба» корреляция копии loopback в микрофоне 0 из 10 (`analyze_tracks.py`) |
| Окна «оба активны» | 10 из 120 (57–77 с) — перекрытие речи видно по двум дорожкам, при смеси его пришлось бы разделять диаризацией |

Замечание: дорожка микрофона содержит **абсолютный цифровой ноль** на 29–56 с и 79–86 с (≥99 % отсчётов равны 0, резкие границы).
Со слов оператора, микрофон глушился то кнопкой на fifine, то mute в Meet; участки не размечались. Причину выяснила контрольная запись
(`mute_test.py`, 80 с, в звонке Meet, оператор говорил всё время; фазы по 15 с, края по 1,5 с отброшены):

| Фаза | Действие | Нулевых отсчётов в дорожке микрофона | RMS |
|---|---|---|---|
| 0–15 с | всё включено | 0,4 % | 0,00829 |
| 15–30 с | mute **только в Meet** | **0,5 %** | 0,00916 |
| 30–45 с | всё включено | 0,4 % | 0,00955 |
| 45–60 с | **кнопка на fifine** (в Meet включён) | **100,0 %** | 0,00000 |
| 60–80 с | всё включено | 0,3 % | 0,01185 |

Выводы (одна пара «fifine + Chrome/Meet», одна запись):
* mute в Meet **не затрагивает сигнал устройства**: loopback-перехват микрофона продолжает писать речь, которую собеседники **не слышат**.
  Транскрипт дорожки «я» поэтому будет содержать реплики, сказанные при выключенном в звонке микрофоне. Это либо нужно показывать
  пользователю, либо надо отдельно узнавать состояние mute (из клиента — не из аудио).
* аппаратный mute даёт цифровой ноль, и его по аудио отличить от «выключен» можно (100 % нулей против 0,3–0,5 % при обычной тишине/речи).

Один звонок, один клиент, одна пара устройств — это проверка механики, а не статистика.

#### Результат: Яндекс.Телемост (приложение, запись 120 с)

Условия: приложение Телемост на ПК, второй участник — телефон в другой комнате с минимальной громкостью динамика, рядом включён телевизор (речь без музыки);
вывод и ввод по умолчанию — Strix Wireless Headset / fifine (по логу), перезапусков потоков нет, overflow 0, CPU процесса записи 0,42 % ядра, память 44 МБ.
Я произносил фразу «Проверка эха, красный апельсин» тремя блоками (≈10–25 с, 50–65 с, 90–105 с), в остальное время молчал.
Источник речи — не звонок людей, а телевизор; запись осталась только в `prototypes/realtime/_local/` (в git не попадает).

| Что проверялось | Результат |
|---|---|
| Речь второго участника в loopback | **да**: активна 116 из 120 с (RMS в среднем 0,092, пик 0,872), распознаётся Whisper large-v3 как цельный связный текст |
| Мой голос в loopback (эхо от клиента/телефона) | **нет**: фраза распознана в дорожке микрофона во всех трёх блоках и **ни разу в loopback**; корреляция моего голоса с loopback в окне ±2,5 с: медиана 0,128, p95 0,252, максимум 0,332 — то же, что у контроля (мои окна против несвязанных моментов loopback: 0,128 / 0,223 / 0,292); порог 0,35 не превышен |
| Речь второго участника в дорожке «я» | **нет**: в расшифровке микрофона только моя фраза; `analyze_tracks.py`: копия loopback в микрофоне в 0 из 46 окон «оба активны» (окно ±0,3 с) |
| Разделение «я»/«остальные» | то, что слышит мой микрофон, и то, что играет приложение, не пересекаются по времени своих реплик |

Ограничения: громкость динамика телефона была минимальной, поэтому петля «телефон → телефонный микрофон → обратно» заглушена по условиям стенда;
в реальном звонке клиенту приходится самому подавлять эхо собеседника, это здесь не проверено. Один клиент, одна запись, одна пара устройств.
Расшифровка дорожки микрофона склеивает паузы в один сегмент (метки времени внутри тишины недостоверны), для оценки окон использован таймлайн
по RMS, а не времена сегментов. Mute в Телемосте и веб-версия клиента не проверялись.

Примечание про глушение чужих звуков: параметр Windows «Communications → Reduce the volume of other sounds» (по умолчанию −80 % при
активности связи) описан в сторонних руководствах; официальная документация не найдена — **не проверено**, как он влияет на
loopback во время звонка. Эхо собственного голоса из-за клиента (sidetone/серверное эхо) тоже не проверялось.

#### Вывод по подходу A

* Рабочая основа: две дорожки, ноль потерь с PyAudioWPatch, ~0,4 % ядра, нагрузка на запись несущественна.
* Условия: клиент звонка должен выводить на то устройство, чей loopback снимается; для чистого «я» нужна гарнитура или AEC;
  дрейф USB-микрофона ~110 ppm надо учитывать, если когда-нибудь потребуется сведение с точностью лучше 100 мс.
* Process loopback на Windows 10 22H2 (build 19045) не работает; на сборках ≥ 20348 — **не проверено**.
* Смена устройства по умолчанию переживается автоматически с потерей ~0,2–0,3 с (`--follow-devices`).
* Открытые вопросы: физическое извлечение наушников, mute мастер-громкости вывода, смена микрофона, остальные клиенты звонков (Teams, Discord, Телемост).

### 2.2. Подход B — браузерное расширение (звук вкладки + микрофон)

**Идея.** Расширение Chrome/Edge (Manifest V3) берёт звук **вкладки** через `chrome.tabCapture` и, отдельно, микрофон, режет на пакеты по 50 мс и по WebSocket
отправляет на приёмник на `127.0.0.1`. Работает только для веб-клиентов (Meet, Teams web, Discord web, Телемост web); десктоп-приложения вне браузера не охватывает.
Прототип: [`prototypes/realtime/browser_extension/`](../prototypes/realtime/browser_extension/README.md), результаты — раздел 5.

### 2.3. Подход C — бот-участник

**Идея.** Сервис заходит в звонок как ещё один участник через официальный API платформы и получает медиа (в идеале раздельно по участникам) вместе с именами.
Прототипа нет, анализ по документации — раздел 6.

* **Что даёт:** потенциально раздельные потоки участников и их идентификаторы без диаризации по голосу; работает без участия пользователя в звонке.
* **Чего стоит:** регистрация приложения, права и согласие администраторов (Teams, Meet), облачная или публично доступная инфраструктура (Teams), закрытая программа доступа (Meet Media API);
  на каждой платформе — разные условия, и они меняются.
* **Видимость:** бот — участник звонка, его видят остальные (в Meet подключение к медиа требует согласия хозяина/организации, см. раздел 6; в Teams бот виден в списке участников — **не проверено**, в Discord
  бот — участник голосового канала). Так что это не «тихая» запись и тем более не заменитель уведомления участников.
* **Юридически:** кроме обязанности предупредить участников, у платформ свои условия. Самое жёсткое из проверенного: Microsoft запрещает использовать Cloud Communications API,
  чтобы записывать или сохранять медиа из звонков и **производные от них данные** — то есть сохранять расшифровки — раздел 6.

### 2.4. Подход D — гибрид

**Идея.** Звук берётся локально (A или B), а метаданные — у платформы или из страницы: список участников, кто сейчас говорит, время входа/выхода. Прототипа нет.

* **Что даёт:** подписи реплик именами без бота и без облака; локально; звук и ASR как в A.
* **Откуда имена:** у API платформ — только после встречи (Meet REST: участники и сессии; Teams Graph: записи звонков и транскрипты, только рабочие/учебные аккаунты тенанта; Телемост API
  участников встречи и говорящего не отдаёт); из DOM страницы (расширение) — только для веб-клиентов, селекторы не документированы и **на живых клиентах не проверялись** (проба написана, `dom.jsonl` в тестах пуст).
* **Чего стоит:** поддержка селекторов под каждую платформу и версию интерфейса; права на сайты в браузере; для API — аккаунты и права платформ.
* **Вывод:** самый дешёвый вариант D — A или B + имена из DOM для веб-клиентов; без проверки на живых клиентах говорить о его надёжности нельзя.

### 3.2. Варианты

* **А. Псевдопоток** (`variant_pseudo.py`): Silero VAD режет живой звук на фразы, faster-whisper расшифровывает каждую после конца речи; ничего не показывается, пока человек говорит. Параметры: пауза конца фразы 500 мс, принудительный разрез каждые 15 с;
  режим `--adaptive`: пауза сокращается с 500 до 150 мс между 5-й и 10-й секундами фразы (режет монолог по естественным паузам).
* **Б. whisper_streaming** (`variant_ufal.py`, политика LocalAgreement-2): раз в 1 с заново декодируется весь не обрезанный буфер (до 15 с), слово показывается, когда два подряд гипотезы с ним согласны.
* **WhisperLiveKit** — **не установлен и не проверен**: `pip install --dry-run` показал, что он обновит в `.venvcuda` numpy до 2.5.4, faster-whisper до 1.2.1 и pydantic — это сломало бы окружение проекта (numpy 1.26.4, pyannote 3.3.2, torch 2.3.1).
  Проверка возможна только в отдельном виртуальном окружении — по правилам задания я его не создавал.

### 3.4. Что происходит при стороннем использовании GPU

Контролируемый тест (`gpu_load.py`: матричная нагрузка CUDA + NVENC, как запись экрана) **не запускался**. Но в первой серии замеров на машине в какие-то периоды работал **посторонний GPU-процесс** (какой — неизвестно, прямо в моём процессе виден скачок
общей занятой памяти GPU и общей загрузки), и эти прогоны показали, что бывает:

* псевдопоток на монологе: время расшифровки фразы выросло с 1,5 до 12,3 с в среднем (максимум 25 с), прогон занял 576 с вместо 433 с, средняя задержка 56 с (вместо 7,6 с);
* LocalAgreement на монологе: 852 с на 433 с аудио, средняя задержка фразы 537 с — поток практически перестал быть «живым»; на диалоге и митинге — отставание 30–500 с;
* итоговый пайплайн на 32-минутной записи в такой период: 1172 с вместо 258 с на чистом GPU (в 4,5 раза дольше).

Вывод: потоковая расшифровка large-v3 на GPU, который делят с чем-то тяжёлым, **не держит реальное время**; нужен запас или запасной вариант (маленькая модель / CPU / отключение живого текста) и проверка отставания очереди во время работы. Сколько именно нагрузки ломает стрим, не измерено.

### 3.5. Стабильность за 30+ минут

**Не измерено** в потоке: прогон реального времени на 32 и 59 минутах не делался (материалы `long32`/`long60` подготовлены, но использованы только для итогового пайплайна). Самый длинный потоковый прогон — 7,7 мин (митинг).

| Митинг, diart только на канале «остальные» (2 голоса B и C) | 12,2 % | 3,0 % | 0,2 % | 9,1 % | 2 | RTF 0,10 |

* Канальное разделение «я»/«остальные» в лаборатории почти идеально (DER 0–0,2 %), потому что в синтетике нет утечки между каналами; на реальном железе утечки при гарнитуре в Б1 не было (0 окон из 10 и 46), а при колонках будет — это не измерено.
* Несколько голосов в одной дорожке (B и C вместе) остаются слабым местом: diart путает похожие голоса (оба синтетических женских) и **склеивает их в одного** (2 найдено вместо 3 на смеси, путаница 9–10 %); офлайн-пайплайн с известным числом голосов — 11 % DER. Различение собеседников внутри «остальных» остаётся задачей модели, а не канала.
* diart на GPU считает быстрее реального времени (RTF 0,10–0,13), задержка структурная 0,5 с; требует этих зависимостей и токена, как и офлайн-пайплайн.

### 3.7. Смешанный язык и смена языка

Материал: 2,3 мин русской речи с английскими репликами и терминами. WER к сценарию (чистый GPU):

| Вариант | WER | CER | Задержка (ср. / p95), с |
|---|---|---|---|
| Псевдопоток adaptive, язык **фиксирован `ru`** | 30,5 % | 26,1 % | 3,5 / 7,4 |
| Псевдопоток adaptive, язык **`auto` на каждую фразу** | **4,0 %** | **4,3 %** | 3,6 / 7,4 |
| LocalAgreement, `ru` | 44,4 % | 40,4 % | 3,9 / 14,1 |
| LocalAgreement, `auto` | 44,4 % | 39,4 % | 3,8 / 12,2 |
| Диаризер (WhisperX, `--lang ru`, офлайн) | 45,0 % (к сценарию) | — | — |

Определение языка **на каждую фразу** решает проблему, когда фразы целиком на одном языке; LocalAgreement и пайплайн с фиксированным языком искажают английские реплики (в `auto` LocalAgreement определяет язык один раз и дальше не меняет). Режим `--lang auto` итогового пайплайна определяет язык один раз на файл —
для чередования языков в одном файле **не проверялся** и, по тому же принципу, вероятно не поможет. Слова-вставки внутри русской фразы (названия, термины) в тесте идут как латиница в сценарии; оценка именно вставок отдельно от целых реплик не делалась.

### 3.8. Схема «поток + запись» и итоговый прогон

Схема: во время звонка идёт поток (текст «вживую»), параллельно пишется полный WAV (шаг Б1: loopback + микрофон, 0,4–0,7 % ядра, 5,76 МБ/мин на дорожку), после звонка обычный пайплайн обрабатывает файл.
Одновременный запуск потока и записи с реальным захватом в Б2 **не проверялся** (запись и ASR измерены по отдельности).

Время итогового прогона `python -m diarrhizer run` (WhisperX large-v3, диаризация, экспорт; включая загрузку моделей; чистый GPU):

| Запись | Время прогона | Доля от длительности |
|---|---|---|
| Смешанный язык, 2,3 мин | 32 с | 0,23 |
| Диалог, 4,9 мин | 52 с | 0,18 |
| Митинг, 7,7 мин | 70 с | 0,15 |
| Монолог, 7,2 мин | 80 с | 0,18 |
| **32 мин** (смесь материалов) | **258 с (4,3 мин)** | 0,13 |
| **59 мин** (смесь материалов) | **427 с (7,1 мин)** | 0,12 |

(На 32-минутной записи в период чужой нагрузки GPU прогон занял 1172 с — в 4,5 раза дольше.)

**Насколько итог лучше живого транскрипта.** По WER на синтетике — **не лучше**: к сценарию пайплайн 1,4 % (диалог) / 3,3 % (митинг) / 5,1 % (монолог), живые варианты 0,8–1,1 % / 2,2–2,7 % / 2,4–3,5 % (см. оговорку про эталон в 3.1). Преимущества итогового прогона в другом: диаризация по голосам с метками слов, согласованная пунктуация и сегментация, единые тайминги,
экспорт в MD/TXT/JSON/SRT, исправление фраз, разрезанных потоком. Сравнение на реальной (не синтетической) речи **не проводилось** — там разница может быть иной.

### 3.9. Рекомендация и чего не стоит делать

* **Для живого текста в MVP:** псевдопоток (вариант А) с `--adaptive`, Whisper large-v3 float16, beam 5, VAD-порог 0,5, пауза конца фразы 500 → 150 мс, предельная фраза 15 с, **язык `auto` на каждую фразу**, отдельный поток на каждый канал («я» / «остальные» из Б1).
  Причины: CPU 12–18 % ядра против 134–142 % у LocalAgreement, предсказуемая задержка (≈ 4–6 с в среднем, p95 ≈ 10–14 с), корректно меняет язык, простая очередь.
* LocalAgreement оставить как опцию для одноязычной русской речи, где нужна меньшая задержка (≈ 2,5–4 с): на диалоге и митинге он лучше, но дороже по CPU/GPU и не переключает язык.
* Итоговый текст всегда делать обычным пайплайном по полной записи (4–7 мин на 30–60 мин записи); живой текст — только подсказка.
* **Не стоит:** запускать стрим large-v3 на GPU, который в этот момент делит игра/рендер/запись экрана без запасного режима (отставание в сотни секунд); принудительно фиксировать язык `ru` при чередовании языков; полагаться на онлайн-диаризацию для различения похожих голосов внутри одной дорожки; ставить WhisperLiveKit в `.venvcuda`.
* Нужно проверить дальше: 30+ минут стрима в реальном времени, контролируемый тест с чужой нагрузкой (`gpu_load.py`), модель `small` и CPU-режим как запасной вариант, одновременный запуск записи и потока.

## 4. Живая саммаризация

Цель: понять, какие настройки частоты и условий вызова модели нужны, чтобы по ходу звонка получать актуальные заметки, не сжигая лимиты и деньги. Продуктовый код не менялся.
Прототип: [`prototypes/realtime/live_summary/`](../prototypes/realtime/live_summary/README.md) — симулятор (`sim.py`), сетка прогонов (`run_grid.py`), таблицы (`report_tables.py`), самопроверка (`selfcheck.py`) и **необязательная** проверка на настоящем провайдере (`live_check.py`, по умолчанию не запускается). Измерено 2026-10-25.

### 4.1. Как проверялось и чему верить

* **Материал:** транскрипты, которые выдал существующий пайплайн на синтетических материалах Б2 (фразы с временами начала/конца и говорящим): диалог 4,9 мин (97 фраз, 635 слов), «шумный митинг» 7,7 мин (165 фраз, 1012 слов), запись 32 мин (543 фразы, 4171 слов; **собрана из повторяющихся материалов**, поэтому метрики покрытия на ней не используются).
  Темп речи ≈ 130 слов/мин. Реальных звонков нет.
* **Проигрыш:** в виртуальном времени шагом 0,5 с (без реального сна; `--speed N` включает сон для проверки глазами). Текст фразы доступен через `asr_latency_s` = 4 с после её конца (Б2: ≈ 4,2 с для псевдопотока), активность речи (VAD) — сразу.
* **Модель — заглушка.** Время вызова = база + на каждую тысячу входных токенов + на каждый выходной токен: профили `api-fast` (1,0 с + 0,4 с/1k + 40 ток/с) и `cli-slow` (8 с + 0,8 с/1k + 25 ток/с) — **предположения**; профиль `cli-codex` **измерен** `live_check.py` на подписочном Codex CLI (12 запросов, 4.7): ≈ 2 с + 30 ток/с и ≈ 12,5 тыс. токенов фиксированного входа в каждом запросе (системная часть самого CLI). Задержки API-провайдеров не измерялись.
  Токены считаются по символам (3,0 символа на токен — как `CHARS_PER_TOKEN` в `summary/chat.py`; реальные токенизаторы различаются). Саммари заглушка строит как «самые информативные фразы, которые влезают в `summary_tokens`» (информативность — редкие слова всего текста; заглушка — модель **ёмкости**, не качества формулировок).
* **Деньги:** формула та же, что у `Provider.estimate_cost` (токены кэша по своим ценам, иначе по цене входа; в прототип не импортируется, правило продублировано и проверено `selfcheck.py`). Три набора цен: `repo-example` — пример из `summary_providers.example.json` (gpt-4o-mini через OpenRouter: 0,15 / 0,6 $ за 1 М, цены кэша не заданы); `cache-50` — то же + чтение кэша за половину входной цены; `anthropic-like` — 3 / 15 $ за 1 М, чтение кэша 0,30, запись 3,75.
  **Наборы `cache-50` и `anthropic-like` — предположения для сравнения, а не прайс-лист;** подставляйте цены своего провайдера (`price_input`, `price_output`, `price_cache_read`, `price_cache_write`).
* **Кэш:** ищется общий префикс с недавним запросом (время жизни 300 с — предположение): `openai-auto` (автоматический, от 1024 токенов, шаг 128, без платы за запись) или `anthropic` (явная точка кэширования в конце стабильной части, запись дороже, от 1024 токенов). Структура запроса в симуляторе: сначала неизменная инструкция, потом контекст, потом изменчивый хвост — как этого требует префиксный кэш.
* **Паузы.** В синтетических материалах паузы между репликами 0,25–0,7 с; в реальных звонках бывают длиннее. Для паузных настроек есть параметр `pause_stretch` (растягивает каждую паузу > 0,3 с, речь не меняется): **x1** — как в материале, **x4** — паузы ≈ 1–2,8 с. Это чувствительность, а не модель реальных пауз; статистику пауз реальных звонков надо снять отдельно.
* **Не измерено:** окна лимитов подписочного CLI (расход плана в процентах), цены и задержки API-провайдеров. Потеря информации и токены/задержка Codex CLI измерены одним коротким прогоном на диалоге 4,9 мин (4 обновления на режим) — 4.7; на длинных звонках дрейф пересказа не проверялся.

### 4.2. Схема триггеров

```
 текст фразы (через ~4 с после её конца) ─┐        VAD: тишина / речь ──────────────┐
                                           ▼                                         ▼
   счётчики «новых слов/реплик»  ───►  [желателен ли вызов?]  ◄── interval_s │ new_words │ new_turns │ pause_s │ ручной
                                           │ да
                                           ▼
                [ждём конец фразы: тишина ≥ silence_ms  ИЛИ  прошло max_wait_s]  ─► нет → ждём
                                           ▼ да
              [нового текста ≥ min_new_words?]  (ручной вызов — без этого условия)
                                           ▼ да
        [не чаще min_interval_s; не больше max_calls_per_hour / max_session_calls; в рамках token_budget / cost_budget_usd]
                                           ▼ да
              [предыдущий вызов ещё идёт?]  ─ да → busy=defer: остаётся «желательным», уходит сразу после завершения,
                                           │            весь накопленный текст — одним вызовом (coalesce)
                                           │          busy=skip: вызов отбрасывается, таймер интервала сбрасывается
                                           ▼ нет
         сборка запроса по режиму контекста (full | window | incremental) → вызов модели → новое саммари на экране
```

### 4.3. Настройки

Все поля — настройки одной «политики» (`Policy` в `sim.py`); значения по умолчанию — пресет «сбалансированно».

| Настройка | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `interval_s` | число / нет | 120 | вызывать каждые N секунд (если есть новый текст) |
| `new_words` | целое / нет | нет | вызывать, когда накопилось N новых слов |
| `new_turns` | целое / нет | нет | вызывать, когда накопилось N новых реплик |
| `pause_s` | число / нет | 6 | вызывать, когда в разговоре тишина ≥ N секунд (только как «ускоритель», см. 4.4) |
| `manual_at` | список времён | пусто | ручные вызовы («обновить сейчас»); минуют `min_new_words` и `min_interval_s` |
| `silence_ms` | целое | 1200 | перед отправкой ждать тишину не короче N мс |
| `max_wait_s` | число | 15 | но не дольше N секунд — потом отправить принудительно |
| `min_new_words` | целое | 40 | меньше нового текста — не вызывать |
| `context` | `incremental` / `full` / `window` | `incremental` | что идёт в запрос: «прошлое саммари + новое» / весь текст / последние M минут |
| `window_min` | число | 5 | размер окна для `window` |
| `busy` | `defer` / `skip` | `defer` | что делать, если прошлый вызов ещё идёт |
| `min_interval_s` | число | 20 | не чаще одного вызова в N секунд |
| `max_calls_per_hour` | целое | 60 | потолок вызовов в час |
| `max_session_calls` | целое / нет | нет | потолок вызовов за сессию |
| `token_budget` | целое / нет | 400 000 | потолок токенов (вход + выход) за сессию |
| `cost_budget_usd` | число / нет | нет | потолок стоимости за сессию (нужны цены провайдера) |
| `summary_tokens` | целое | 600 | размер саммари, который просим у модели |
| провайдер, модель живого режима | строки | отдельно от обычной саммаризации | (в симуляторе — профили модели; в продукте — отдельные настройки, см. 4.8) |

Зарезервированные wildcard-ы живого режима: `{{previous_summary}}` (прошлое саммари) и `{{new_text}}` (реплики, пришедшие с прошлого вызова); `{{transcript}}` в режимах `full`/`window` — весь текст или окно.
**Порядок в шаблоне важен для кэша:** сначала неизменная инструкция, потом контекст, изменчивое (`{{previous_summary}}`, `{{new_text}}`, `{{duration}}`, `{{note}}`) — в конце; любое изменчивое значение в начале ломает префикс.

### 4.4. Решения и обоснование

* **Перекрытие вызовов: `busy=defer` с объединением текста (coalesce).** Текст при пропуске не теряется (он копится и уходит со следующим вызовом), поэтому выбор — между свежестью и ценой. На быстром провайдере перекрытий нет вообще (T3: api-fast даёт 0 пропусков/ожиданий при любом из вариантов);
  на медленном (`cli-slow`, предположение) при вызове «каждые 30 с по всему тексту» `defer` делает 54 вызова со средним возрастом саммари 60 с, а `skip` — 35 вызовов (30 пропусков) со средним возрастом 71 с и на 36 % дешевле. Берём `defer` по умолчанию (свежее, текст не теряется, расход ограничен `min_interval_s` и лимитами), `skip` — для режима «экономить». Замер на Codex CLI показал вызов 10–26 с (в среднем 12–16 с), то есть **быстрее, чем предполагал профиль `cli-slow`**: перекрытия начинаются только при интервале порядка 15–30 с.
* **Паузный триггер — только добавка к интервалу.** Один `pause_s` без интервала ненадёжен: на материале с короткими паузами сработал 1 раз за 32 мин (возраст саммари недоступен), даже при растянутых паузах (x4) — 10 раз и возраст 163 с (T4). Вместе с `interval_s` (и `min_interval_s` как предохранителем) он ускоряет вызов в естественных паузах.
  `pause_s` = 2 при растянутых паузах превращает «120 с или пауза» в 60 вызовов за 32 мин (вместо 22): цена ×2,4, возраст 80 → 43 с (T4) — то есть порог паузы надо подбирать по реальным звонкам, потому что он напрямую задаёт частоту вызовов.
* **Ожидание конца фразы нужно, но на синтетике его эффект не виден:** паузы 0,25–0,7 с короче `silence_ms`, поэтому вызов всегда ждёт `max_wait_s`; на реальных паузах ожидание закончится раньше.
* **Режим контекста:** см. 4.6–4.7 (инкрементально дёшево без кэша; весь текст сопоставим по цене при сильной скидке на кэш и не теряет информацию; окно забывает начало).
* **Свежесть имеет пол ≈ 20 с** независимо от настроек: задержка ASR (4 с) + время генерации саммари на 600 токенов (≈ 15 с при 40 ток/с) + ожидание триггера; чаще раза в минуту на таком провайдере выигрыш мал: «каждые 30 с» против «каждые 60 с» даёт возраст 41 против 54 с при цене в 1,7 раза выше (T1, A против B).

### 4.6. Что показали таблицы

**T1.** Стоимость в основном определяется контекстом и частотой: при ценах репо «каждые 30 с, весь текст» (A) — 0,131 $/час, «120 с или пауза, инкрементально» (G) — 0,017 $/час, а свежесть при этом 41 против 90 с. Весь текст растёт вместе со звонком: вход одного вызова к 32-й минуте доходит до ≈ 10,5–11,2 тыс. токенов (A, B), у инкрементального — 1,3–1,8 тыс. и почти не растёт.
**Окно 5 мин** (C, I) вдвое дешевле полного текста без кэша, но не помнит начало: покрытие «фактов» первой половины митинга в нём 0,20 против 0,29 у полного и инкрементального (T6, заглушка).

**T2. Где кэш префикса помогает, а где нет.**
* **Весь текст** — единственный режим, где префикс (инструкция + весь прошлый текст) растёт и совпадает с прошлым запросом: **86–94 % входных токенов берутся из кэша**. При скидке 50 % цена падает на треть (0,078 → 0,052 $/час), при скидке 90 % (anthropic-подобные цены) — в 2,2 раза (1,67 → 0,74 $/час при «каждые 60 с»; 0,79 → 0,38 при «сбалансированно»), и тогда **весь текст стоит столько же, сколько инкрементальный** (0,382 против 0,385 $/час) и не теряет информацию.
* **Инкрементальный** режим кэшу почти не помогает: общий префикс — только инструкция (300 токенов < 1024). Если сделать инструкцию длиннее порога (1500 токенов), в кэш уходит 50–58 % входа, но выигрыш невелик (0,022 → 0,019 $/час с кэшем −50 %), а без скидки инструкция просто удорожает запрос (0,017 → 0,022).
* **Скользящее окно** кэшу не помогает (префикс сдвигается каждый вызов: 0 % из кэша) и при **явной точке кэширования с платой за запись вредно**: 0,451 против 0,412 $/час без кэша — запись оплачивается, а читать нечего. Для окна и инкрементального режима точку кэширования ставить не надо.
* Ограничения: время жизни кэша 5 мин (предположение) — при интервале ≥ 5 мин префикс умирает, и режим «весь текст» теряет выигрыш (пресет «экономно» с интервалом 5 мин кэшем не пользуется); у подписочных CLI токены не тарифицируются, а Codex с продолжением сессии отправляет только новое сообщение,
  но «биллится» (по лимитам) весь контекст, в основном как кэшированный (docs/cli-sessions.md) — это четвёртый режим, `session`, в симуляторе не моделируется.

**T3, T4** — выводы в 4.4. **T5.** Пресеты на трёх материалах: «экономно» — 11–14 вызовов/час, возраст саммари ≈ 175 с; «сбалансированно» — 33–42 вызова/час (при реальных паузах x4), возраст 64–80 с; «часто» — 83–111 вызовов/час, возраст 38–46 с.

**Подписочный CLI (измерено на Codex, T7/T8).** Каждый запрос несёт ≈ 12,5 тыс. токенов фиксированного входа (≈ 11,3 тыс. из них приходят из кэша), поэтому **режим контекста почти не влияет на расход**: на диалоге 4,9 мин вход был 13,8–18,9 тыс. токенов и у инкрементального режима, и у «всего текста» (14,3–18,6 тыс.).
Расход определяет число вызовов: «сбалансированно» ≈ 0,5 млн токенов в час (≈ 90 % из кэша), «часто» ≈ 1,3 млн, «экономно» ≈ 0,18 млн. Потолок `token_budget` = 400 тыс. токенов за сессию на таком провайдере кончается за ≈ 28 вызовов (≈ 45 минут при «сбалансированно»): для CLI потолок надо задавать числом вызовов или считать
только не-кэшированные токены. Сколько это в процентах окон лимита плана — **не измерено** (`live_check.py` лимиты не читает).

### 4.9. Как это ляжет на текущую структуру (без реализации)

* **`adapters/llm.py`** — без изменений в логике: уже есть `complete_chat` с блоками `Block(cache=True)`, `LLMReply.usage` (вход/выход/кэш), `cost_usd` и `cache_available`. Живая сессия строит запрос блоками «инструкция (кэш) → контекст → изменчивый хвост» и копит учёт токенов и стоимости из ответов; точку кэширования ставит только в режимах `full` и `session`.
* **`summary/wildcards.py`** — два новых wildcard-а в реестре, помеченные «только живой режим»: `{{previous_summary}}`, `{{new_text}}`; обычная саммаризация ими пользоваться не может (ошибка валидации с понятным текстом), `--list-wildcards` показывает их отдельным блоком.
* **`summary/templates.py`** — встроенные шаблоны живого режима (инкрементальный и «весь текст») и признак «живой» у шаблона; пользовательские шаблоны остаются в том же JSON.
* **Новый модуль `summary/live.py`** (план): `LivePolicy` (поля из 4.3, проверка значений), планировщик как чистая функция состояния (то, что сейчас делает `run()` симулятора: вход — события «текст», «речь/тишина», «ручной», «вызов завершён»; выход — «вызвать сейчас» и причина), учёт лимитов, запись `live/summaries.jsonl` в папку задания (каждый вызов: время, режим, токены, стоимость, кэш, текст).
  Симулятор остаётся как режим «репетиции» без сети (`live --replay <job>`).
* **`summary/providers.py`** — отдельный выбор провайдера и модели для живого режима (отдельный ключ в `summary_providers.json`, например `"live": {"provider": ..., "model": ...}`; модель переопределяется поверх копии `Provider`, ключи по-прежнему из окружения). Подписочные CLI: параллельные вызовы и частые запросы упираются в лимиты плана (`Limits`) — планировщик читает `Limits.allowed` и останавливается.
* **GUI (`diarrhizer_gui`)**: экран живого режима (новая вкладка/панель рядом с монитором): живой текст, панель заметок, кнопка «Обновить сейчас» (`manual_at`), строка состояния («следующее обновление через…», вызовов, токенов, потрачено), выбор пресета и раскрывающиеся расширенные настройки; в `summary_settings_screen.py` — группа «Живое саммари» (провайдер/модель, пресет, лимиты). Вызовы идут через уже существующий `llm_worker.py` (дочерний процесс, отмена, таймаут).
* **CLI**: команда `python -m diarrhizer live` — захват (Б1) + потоковый текст (Б2) + живые заметки; опции зеркалят поля политики (`--preset`, `--interval`, `--live-provider`, `--live-model`, `--max-cost` …), `--print` выводит заметки в консоль, `--replay <job>` — репетиция на готовом job без вызовов модели. Точки входа `doctor`, `run`, `summarize` не меняются.
* **Правила проекта:** семантические теги для нового модуля и публичных настроек, обновление README/docs, тесты планировщика (те же проверки, что в `selfcheck.py`: лимиты, бюджет, ручной вызов, правило цены).

### 4.10. Вопросы к решению

1. **Режим по умолчанию: инкрементальный или «весь текст».** Измерено на Codex: инкрементальный не уступил полному (4 обновления). У подписочного CLI режим расход почти не меняет (фиксированные ≈ 12,5 тыс. токенов на запрос), у API без кэша инкрементальный дешевле в 2,2 раза, при скидке 90 % на кэш они стоят одинаково. Предлагается инкрементальный по умолчанию; «весь текст» — для провайдеров с дешёвым кэшем и интервалом < 5 мин. Нужна проверка на длинном звонке (20+ обновлений).
2. **Провайдер живого режима:** подписочный CLI работает (вызов 12–16 с), но тащит ≈ 12,5 тыс. токенов накладных расходов на запрос и неизвестно, как это ложится на окна лимитов; API с ценой быстрее считается, но задержки/цены API не измерены.
3. **Что считать бюджетом и что делать при его исчерпании:** потолок в токенах не годится для CLI (кончается за ≈ 28 вызовов), нужен потолок в вызовах или в не-кэшированных токенах; по исчерпании — остановить живые заметки с уведомлением (предлагается) или перейти на ручной режим.
4. **Пороги пауз** (`pause_s`, `silence_ms`) надо снять с реальных звонков: на синтетике они не проверяются.
5. **Приватность:** живой режим отправляет текст идущего разговора во внешний сервис каждые 1–2 минуты; с локальной моделью (Ollama) этого нет. Требует отдельного явного согласия пользователя и предупреждения участников (раздел 6.5).
6. **Показывать ли историю заметок** или только последние (влияет на формат записи в `live/summaries.jsonl` и на GUI).

## 5. Расширение браузера (подход B)

Проверка 2026-10-24: Chrome 155 (у оператора), Edge 155 (автоматизация, частично). Код: `prototypes/realtime/browser_extension/` — Manifest V3, service worker,
offscreen-документ (`USER_MEDIA` + `AUDIO_PLAYBACK`), AudioWorklet, WebSocket на приёмник; приёмник `receiver.py` на стандартной библиотеке.

**Как устроено (по официальной документации).**
* `chrome.tabCapture.getMediaStreamId()` отдаёт одноразовый идентификатор потока вкладки; захват разрешён только после «вызова» расширения пользователем (кнопка, как у `activeTab`),
  захват продолжается при навигации и останавливается, когда вкладка закрыта ([developer.chrome.com, tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture), обновлено 2026-09-11).
* После получения потока вкладка перестаёт звучать у пользователя; чтобы звук остался, поток нужно проиграть обратно через `AudioContext` — в прототипе так и сделано (там же).
* Service worker не умеет `AudioContext`, поэтому звук обрабатывается в offscreen-документе ([chrome.offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen), обновлено 2026-09-21);
  документ с причиной `AUDIO_PLAYBACK` закрывается через 30 с без звука, поэтому в прототипе используется комбинация `USER_MEDIA` + `AUDIO_PLAYBACK`.

**Результаты на машине оператора (Chrome 155, вкладка с воспроизводимым звуком, не звонок).**

| Что проверялось | Результат |
|---|---|
| Звук вкладки у пользователя в наушниках во время захвата | **не пропадает** (со слов оператора, всё время) |
| Файл вкладки `tab_5`: длина / стенные часы | 13,2 с аудио за 13,2 с, расхождение −25,7 мс |
| Файл микрофона `mic_4` | 33,4 с аудио за 33,4 с, расхождение −6,6 мс |
| Потери пакетов (`seq_gaps`, `missing_packets`) | **0 / 0** в обоих файлах; интервал прихода пакетов: медиана 50,0 мс, p99 ≈ 51 мс, максимум 51,5 мс |
| Закрытие вкладки с захватом | файл вкладки корректно завершается, **микрофон продолжает писаться** (со слов оператора) |
| Переключение на другую вкладку | захват не прерывается по документации; отдельно от закрытия не измерялось |
| Приёмник: чужая страница, чужой Host, неверный секрет | отказ во всех трёх случаях (проверено скриптом: 403 / 403 / закрытие с кодом 4401) |
| Автоматическая проверка в Edge | расширение грузится (`--load-extension` в Edge 155 работает), но `tabCapture` не стартует без настоящего вызова пользователем («Extension has not been invoked for the current page») — программно имитировать нельзя |

**Что не проверено.**
* Реальные веб-клиенты: Meet, Teams (web), Discord (web), Телемост (web) — **не проверено** (нужен вход в звонок; записывается только тестовая комната).
* Чтение имени говорящего и списка участников из DOM — проба написана (`dom_probe.js`: счётчики и тайминги по сигнатурам элементов, без имён), на живых клиентах **не запускалась**.
* Что показывает Chrome при установке и при запросе доступа к сайтам: по справке `activeTab` не показывает предупреждения ([permission warnings](https://developer.chrome.com/docs/extensions/develop/concepts/permission-warnings), 2024-02-05);
  для `tabCapture`, `offscreen`, `storage`, `scripting` и для опциональных host-прав справка текст не приводит — **не проверено**.
* Firefox и другие браузеры — не рассматривались.

**Стоимость поддержки (оценка по устройству решения, без проверки на живых клиентах).**
* Платформ: 4 веб-клиента × Chromium-браузеры (Chrome, Edge). Десктоп-клиенты (Телемост, Teams, Discord) расширением не покрываются — для них остаётся A.
* Звук: механизм одинаков для всех сайтов и от версий интерфейса не зависит — хрупкой частью он не является. Хрупко только чтение имён: селекторы Meet / Teams / Discord / Телемоста
  не документированы, меняются без предупреждения, каждая платформа требует своих правил и регулярной перепроверки (число селекторов и частота поломок **не измерены**).
* Права: звук вкладки — `tabCapture` + `activeTab` (без прав на сайты); доступ к сайтам звонков нужен только для DOM-пробы и запрашивается во время работы (optional host permissions).
* Распространение: прототип загружается вручную («Загрузить распакованное»); в Chrome 137+ флаг `--load-extension` в официальных сборках удалён (объявление
  [2025-04-04](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY/m/S0ET5wPjCAAJ)), автоматизация возможна на Chromium / Chrome for Testing / Edge. Публикация в магазине не проверялась и не планировалась.
* Требует клика пользователя на каждый звонок (начало захвата), «фонового» режима нет — это защита, а не недостаток.

## 6. Ограничения платформ и юридические замечания

Проверено по официальным страницам **2026-10-24**; даты — это «обновлено» из метаданных страницы, где они были; где даты нет — так и указано.

### 6.1. Яндекс.Телемост

* Публичный API — REST для управления встречами, трансляциями и перепиской; **только для пользователей Яндекс 360 для бизнеса с аккаунтами на домене организации**
  ([о сервисе](https://yandex.ru/dev/telemost/doc/ru/index.md), даты на странице нет).
* Права OAuth: `telemost-api:conferences.create/read/update`, `telemost-api:organization_settings.read/update`
  ([доступ к API](https://yandex.ru/dev/telemost/doc/ru/access.md), даты нет). Оглавление документации: конференции (создание, просмотр, изменение), соучастники (cohosts), настройки.
* **Записи, субтитров, транскрипта, списка говорящих и аудио участников в API нет** (по оглавлению
  [llms.txt](https://yandex.ru/dev/telemost/doc/ru/llms.txt?revision=r21356348)); получить звук участников программно нельзя. Раздельные потоки — не доступны.
* Пользовательская функция записи встречи в справке упоминается, но условия (кто пишет, куда, уведомление участников) получить не удалось — **не проверено**; условия использования на запись не проверялись.
* On-prem: API облачный, звука не даёт; локальные подходы — A (проверено) и B (механизм проверен на произвольной вкладке).

### 6.2. Google Meet

* **Meet Media API** (звук/видео в реальном времени): **«больше не принимает новые заявки»** (Developer Preview), страницы обновлены 2026-10-01
  ([обзор](https://developers.google.com/workspace/meet/media-api/guides/overview), [начало работы](https://developers.google.com/workspace/meet/media-api/guides/get-started)).
  Права OAuth — `meetings.conference.media.readonly` (+ `.audio.` / `.video.`), все *restricted*, плюс `meetings.space.read`; серверы с такими данными проходят проверку безопасности; нельзя для аккаунтов несовершеннолетних.
* Условия подключения: хозяин должен разрешить в настройках календаря, иначе подключение отклоняется; для Workspace-встречи согласие даёт участник из организации-владельца, для обычной (gmail) — инициатор, который должен быть в встрече;
  зашифрованные и с водяным знаком встречи не подключаются; согласие можно отозвать в любой момент. Участники должны иметь минимальные версии приложений (Meet Android 309 и т. д.).
* Аудио: приходят «виртуальные» потоки через SFU, при превышении лимита — только «самые релевантные» участники; источник пакета определяется по CSRC. Точное число потоков страница не называет.
* **Meet REST API**: после встречи — записи (MP4, в Drive организатора), транскрипты (Docs в Drive; записи реплик доступны 30 дней), умные заметки, участники и сессии;
  в реальном времени — только события через Workspace Events API, не медиа ([обзор](https://developers.google.com/workspace/meet/api/guides/overview), 2026-09-14).
  Транскрибация доступна в перечисленных тарифах Workspace (Business Standard/Plus, Enterprise, Education Plus, Workspace Individual и др.); участники видят предупреждение, админ может требовать явное согласие
  ([справка Meet](https://support.google.com/meet/answer/12849897), даты нет).
* Вывод: раздельный поток каждого участника в реальном времени для нового разработчика сейчас **недоступен**; REST — только постфактум, в облаке Google (Drive организатора), не локально.

### 6.3. Microsoft Teams

* **Бот с доступом к медиа** (application-hosted media): только C#/.NET (`Microsoft.Graph.Communications.Calls.Media`); C++ и Node.js реальное медиа **не поддерживают**; в продакшене — Windows Server в Azure с публичным IP на каждый инстанс
  (локальный Windows Server допускается только для разработки/тестов), не Azure web app; не менее 2 ядер CPU; платформа real-time media остаётся в developer preview
  ([требования](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/requirements-considerations-application-hosted-media-bots), обновлено 2026-07-22).
* Права Graph: `Calls.AccessMedia.All`, `Calls.JoinGroupCall.All` и др. — выдаёт администратор тенанта ([обзор Cloud Communications API](https://learn.microsoft.com/en-us/graph/api/resources/communications-api-overview), обновлено 2025-08-02);
  регистрация бота — манифест с `supportsCalling`/`supportsVideo` + согласие администратора ([обзор ботов](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/calls-and-meetings/calls-meetings-bots-overview), 2026-05-29).
* **Условие Microsoft: «You may NOT use the Cloud Communications APIs to record or otherwise persist media content from calls or meetings that your application accesses, or data derived from that media content»** (обзор Cloud Communications API, там же) — то есть через этот API
  нельзя сохранять ни запись, ни производные данные (расшифровку); для нашего сценария это блокирующее ограничение, юридическую трактовку надо уточнять у юриста.
* Раздельный звук участников (unmixed): в официальной документации, которую удалось открыть, не подтверждён — **не проверено** (сторонний сервис Recall.ai заявляет раздельные потоки Teams по флагу у себя, это не документация Microsoft).
* Транскрипты после встречи через Graph: `OnlineMeetingTranscript.Read.All` (делегированные — только рабочие/учебные аккаунты, **личные Microsoft-аккаунты не поддерживаются**), для приложений нужна application access policy; тенант-админ может отключить доступ к транскриптам
  или атрибуцию говорящих ([callTranscript](https://learn.microsoft.com/en-us/graph/api/calltranscript-get), 2026-10-01). Живой транскрипт в реальном времени в этих материалах не описан — **не проверено**.
* Клиент: при начале записи все участники получают уведомление в Teams; гости записывать не могут ([справка Microsoft](https://support.microsoft.com/en-us/office/record-a-meeting-in-microsoft-teams-34dfbe7f-b07d-4a27-b4c6-de62f1348c24), даты нет).
  Локальный захват звука этого уведомления не вызывает — **не проверено**, обязанность предупредить участников остаётся.
* On-prem: бот с медиа требует Azure/публичной инфраструктуры и запрещает сохранение — **не совместимо** с «локально». Остаются A и B.

### 6.4. Discord

* Голос и видео во всех звонках (DM, группы, голосовые каналы, Go Live; кроме stage-каналов) сквозно шифруются протоколом **DAVE**; миграция завершена в начале марта 2026
  ([блог Discord, 2026-05-18](https://discord.com/blog/every-voice-and-video-call-on-discord-is-now-end-to-end-encrypted)); E2EE-звонки обязательны с 1 марта 2026, боты объявляют поддержку через `max_dave_protocol_version`, рекомендован голосовой шлюз v8
  ([Voice Connections](https://docs.discord.com/developers/topics/voice-connections), даты нет).
* Приём голоса ботом: в документации UDP-канал описан как несущий принимаемый и отправляемый голос, но **пошагового описания приёма, соответствия SSRC пользователям и декодирования входящего Opus нет**; расшифровка DAVE описана частично, остальное — отсылка к libdave и протоколу.
* Библиотеки: у discord.js voice приём аудио не документирован Discord, поэтому «стабильная поддержка не гарантируется», DAVE — через `@snazzah/davey`
  ([документация discord.js](https://discord.js.org/docs/packages/voice/stable)); у Pycord есть запись/прослушивание (`start_recording`, `start_listening`), расшифровка работает только в звонках, перешедших на DAVE; в основной ветке discord.py
  поддержка приёма голоса и DAVE **не найдена — не проверено**; привязки libdave для других языков в основном без документации.
* Раздельные потоки участников: техническая возможность есть (приём идёт по отправителям), но она не документирована и зависит от библиотек.
* Правила разработчиков по записи голоса: официальную страницу открыть не удалось (ошибка DNS) — **не проверено**; права на получение/хранение голоса пользователей и согласие — отдельный вопрос юриста.
* On-prem: бот работает с локальной машины (исходящие соединения) — по требованию «локально» совместим, но легальность и стабильность — под вопросом.

### 6.5. Юридическое замечание

* **Запись и расшифровка разговора требуют уведомления и/или согласия участников**; правила зависят от юрисдикции (где-то достаточно согласия одной стороны, где-то нужно согласие всех).
  Платформы могут запрещать запись условиями использования и показывать индикатор записи, который при локальном перехвате звука не появляется (Teams — **не проверено**) — это не отменяет обязанность предупредить собеседников.
  Это не юридическая консультация; конкретные нормы и условия сервисов (кроме процитированных выше) не проверялись. Для тестов использовались только собственные материалы и тестовые комнаты.

### 6.6. Технические ограничения подходов A и B

* A: loopback зависит от выбранного клиентом устройства; process loopback требует build ≥ 20348 (на Windows 10 22H2 не работает); в тишине WASAPI loopback не присылает пакетов; mute в клиентском приложении сигнал микрофона не обнуляет.
* B: только веб-клиенты в Chromium-браузерах; старт захвата — только по клику/сочетанию клавиш пользователя на каждом звонке; автоматическая проверка невозможна без настоящего вызова.
